01 / System Overview

Operational Scope

The Adullam project includes the public institutional website, the admission application portal, the student dashboard, and the administrative dashboard. The active business workflows are concentrated in dashboard/. Root-level files serve public website pages, while admin/ and user/ contain legacy interfaces that should be preserved until formally retired.

Public websiteProgram pages, admissions information, requirements, contact page, modal content, and public assets.
Student portalRegistration, verification, application form, document upload, tuition proof, hostel registration, and profile security.
Administrative portalApplicant review, admission decisions, payment verification, hostels, analytics, reporting, settings, and user management.

05 / Workflows

Core Operational Workflows

Applicant Lifecycle

  1. Applicant registers and verifies email.
  2. Applicant sets password and logs in.
  3. Applicant completes the multi-step application form.
  4. System requests recommendations where applicable.
  5. Admin reviews submitted application and documents.
  6. Admin admits or rejects the applicant.
  7. Admitted applicant downloads admission letter and uploads tuition proof.
  8. Admin verifies tuition payment and onboards eligible online students.
  9. Eligible onsite or returning students register for hostel when the window is open.

Administrative Operations

  • Use cohort filters consistently across dashboards, applicant lists, analytics, and exports.
  • Use system_settings for registration windows and active cohort configuration.
  • Use manage_programs and focus-area pages for program structure.
  • Use broadcast_email and broadcast_cron.php for email campaigns.

08 / Future Implementation

Online Payment Gateway With Flutterwave

A recommended future enhancement is to replace manual payment-proof-only workflows with Flutterwave-powered online payments for application fees and tuition payments. Manual uploads may remain available as an administrative fallback.

Objective: provide secure card, transfer, USSD, bank, and mobile-money payment options while automatically reconciling payment status inside the portal.

Application Fee Payment

  • Add a payment step before final application submission or immediately after account verification.
  • Create an application_payments table with user_id, application_id, amount, currency, flutterwave_tx_ref, flutterwave_transaction_id, status, paid_at, and raw webhook response fields.
  • Generate a unique transaction reference per applicant and cohort.
  • Redirect the applicant to Flutterwave Checkout or embed the Flutterwave inline payment flow.
  • Verify payment server-side using Flutterwave transaction verification before marking the application fee as paid.
  • Prevent final application submission unless the fee is paid or an admin grants an exception.

Tuition Payment

  • Extend or replace the current tuition_payment proof workflow with online payment records.
  • Support full tuition and installment payments if the institution approves a payment plan.
  • Store each transaction separately and compute outstanding balance from verified transactions.
  • Automatically update tuition status to approved after successful Flutterwave verification.
  • Keep manual proof upload as a fallback for offline bank transfers or exceptional cases.

Webhook and Reconciliation Requirements

  • Create a secure webhook endpoint such as /dashboard/webhooks/flutterwave.
  • Validate Flutterwave webhook signatures before processing events.
  • Always verify transactions against Flutterwave's API before trusting webhook data.
  • Make webhook processing idempotent so duplicate events do not double-credit payments.
  • Add admin reconciliation screens for successful, pending, failed, reversed, and disputed payments.
  • Log all payment events for auditability.

Configuration and Security

  • Store Flutterwave public key, secret key, encryption key, and webhook secret outside tracked code.
  • Use test keys in development and live keys only in production.
  • Restrict payment verification endpoints to server-side calls.
  • Never expose Flutterwave secret keys to JavaScript or public HTML.

Suggested Implementation Sequence

  1. Define approved fee rules by program, mode, nationality, and cohort.
  2. Add payment tables and migration scripts.
  3. Build application fee payment initiation and verification.
  4. Add Flutterwave webhook endpoint and event logs.
  5. Add tuition payment initiation and installment support if required.
  6. Add admin reconciliation and export reports.
  7. Run end-to-end tests in Flutterwave sandbox before enabling live keys.
09 / Monitoring

Site Watch Alerts

site_watch.php provides application-level monitoring for PHP warnings, fatal errors, uncaught exceptions, and suspicious request patterns. It is loaded from both root db.php and dashboard/db.php, which covers most dynamic public and dashboard requests.

Alert recipientsnoahabayomi14@gmail.com and ngbedebarnabas@gmail.com
Log fileslogs/site_watch.log for events and logs/site_watch_alerts.json for email rate limiting.

What It Detects

  • PHP runtime warnings, recoverable errors, fatal shutdown errors, and uncaught exceptions.
  • Common SQL injection, cross-site scripting, path traversal, sensitive-file probe, remote-code-execution probe, and scanner-user-agent patterns.
  • Request context such as URL, method, IP address, user agent, referrer, session role, and sanitized GET/POST values.
Site Watch is not a complete security platform. Keep using Hostinger server logs, malware scanning, backups, HTTPS, secret rotation, GitHub secret scanning, and WAF/CDN protection where available.

By default, suspicious traffic is reported but not blocked because false positives can interrupt real applicants. Blocking can be enabled by setting SITE_WATCH_BLOCK_THREATS to true after testing.

10 / Security

Security and Access Control

Rotate any database, SMTP, Google, Flutterwave, or SSH credentials that have been committed or shared. Store secrets outside tracked source code where possible.
  • Change seeded admin and superadmin passwords after database import.
  • Protect SQL dumps and production backups.
  • Verify uploaded files cannot execute PHP.
  • Use HTTPS in production.
  • Keep Composer dependencies patched within PHP version constraints.
  • Review role checks before adding or exposing admin pages.
11 / Maintenance

Maintenance Reference

Email

Dashboard email uses dashboard/mailer.php. Test registration, password reset, profile OTP, recommendation, admission, and payment-related emails after mailer changes.

Monitoring

Review logs/site_watch.log when an alert arrives. Repeated identical email alerts are rate-limited for 15 minutes through logs/site_watch_alerts.json.

Scheduled or Cron-style Scripts

  • dashboard/onboarding_cron.php
  • dashboard/broadcast_cron.php
  • backup_generate.php, backup_to_drive.php, and backup_upload.php

Known Technical Debt

  • Multiple application generations exist in one repository.
  • There are multiple database connection files.
  • Some legacy pages contain old encoding artifacts.
  • Some dependencies are duplicated in legacy folders.
  • Deployment asset exclusions should be reviewed before changing public images.
11 / Transition

Project Transition Protocol

This section defines the recommended transfer process for a developer assuming responsibility for maintenance or further development.

Repository Access

  1. Add the developer as a GitHub collaborator using the minimum access level required.
  2. Use Write access for normal development work.
  3. Grant environment secret or deployment access only if deployment responsibility is included in the engagement.

Required Transfer Materials

  • Current database export delivered through a secure channel.
  • Production database credentials, or a rotated credential set.
  • SMTP credentials, or a newly generated mail account/app password.
  • Hosting control panel and SSH deployment context if production deployment is part of the role.
  • Google API credentials if backups or Google integrations are in scope.

Acceptance Checks

  1. Run the project locally and confirm clean URLs work.
  2. Log in as student, admin, and superadmin.
  3. Test registration, email verification, password reset, profile OTP, application submission, admin review, admission decision, tuition workflow, and hostel registration.
  4. Confirm GitHub Actions deployment and rollback procedures with a non-critical release where possible.
  5. Review the future Flutterwave implementation plan before beginning online payment work.
